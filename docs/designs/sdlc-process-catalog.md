## Problem Statement

Engineering orgs need a complete, navigable reference of SDLC processes organized by
category (Monitoring, Testing, and so on), where each process has uniform depth: purpose,
best practices, automation, signals. Today two things exist and neither works:

- **Formal maturity models** (ISO/IEC 12207, CMMI, Microsoft SDL) are heavy, phrased for
  auditors, and unusable day-to-day.
- **Awesome-lists** ([Awesome-SDLC](https://github.com/doshyt/Awesome-SDLC),
  [awesome-software-engineering](https://github.com/Alliedium/awesome-software-engineering))
  are bookmark dumps with no per-process depth and no way to track what you've adopted.

The structured, machine-readable, self-assessable version of this exists only for security:
[OWASP SAMM](https://owasp.org/www-project-samm/) and
[OWASP DSOMM](https://dsomm.owasp.org/about). Nothing covers the whole lifecycle. Every
engineering org rebuilds a worse version of it in Confluence.

## What Makes This Cool

**The gap is specific and real: there is no DSOMM for the whole SDLC.** Catalogs get built
security-first because security is the only place compliance forces a budget. The general
case has no equivalent.

**Completeness is the product, not the taxonomy.** Human-curated catalogs stall around 40
entries because writing entry 41 is unpaid work with no audience. That is exactly why
general-purpose lists degenerate into link dumps while DSOMM (narrow scope, funded
attention) achieves real depth. AI generation with human approval is what makes 400+ entries
at uniform depth reachable. At 60 entries this is one more awesome-list. At 400 with real
citations it is the reference.

**Two audiences, one artifact.** Because entries are markdown with structured frontmatter,
the same repo serves humans (a searchable site) and agents (a versioned `catalog.json`).
An awesome-list cannot do the second thing.

## Constraints

- Open source, public repo, published upon initial data generation.
- 99% AI-managed: generation must be a repeatable skill, not a one-off prompt.
- Must publish to GitHub Pages or equivalent, at $0 hosting cost.
- Must be structurally ready for per-project status tracking without becoming a SaaS.
- Must remain open to human PRs for corrections and additions.

## Premises

All six confirmed by the user during the session.

1. **Stable IDs, not paths, are process identity.** Per-project status tracking means every
   process needs an immutable key that survives renaming and re-categorization. One-way door.
2. **The taxonomy is a graph, not a tree.** "Performance monitoring" and "Performance
   testing" are one concern in two lifecycle phases. Folders give navigation; frontmatter
   tags and explicit `related:` links give the real relationships.
3. **Never build a backend.** DSOMM proves status tracking needs no server. A user's status
   lives in their own repo; notes are private because they are in the user's repo, not
   because auth was built.
4. **Uncited AI content gets dismissed as slop.** Reputational one-way door. Every entry
   carries `sources:` pointing at real standards. This is also the quality gate that stops
   the generator inventing practices.
5. **"AI-managed" and "open to PRs" conflict, and CI resolves it.** State explicitly what a
   human PR is for, and enforce the machine-readable contract with schema validation so a PR
   cannot silently break the data format.
6. **Distribution is the risk, not the build.** The pain here is chronic, not acute; nobody
   is on fire. This project fails by being unfound. So ship a versioned machine-readable
   release artifact, not just a website.

## Approaches Considered

### Approach A: Markdown-first, minimal
Markdown + frontmatter, folders by category, Material for MkDocs, stable IDs, no schema
enforcement or data layer. S effort, Low risk. **Rejected:** uniformity across 400
AI-generated entries rests on discipline alone, and discipline loses to volume. Retrofitting
a schema later means rewriting entries.

### Approach B: Markdown-as-source with enforced schema and generated data layer
A, plus JSON Schema validation in CI, a required-heading linter, generated
`catalog.json`/`catalog.yaml` release artifacts, a `status-schema.json`, and two AI
generation skills. M effort, Low-Med risk. **Chosen.**

### Approach C: Catalog as a package plus CLI
All of B, plus an `sdlc-check` CLI, npm/PyPI publishing, and a README badge. L effort, Med
risk. **Deferred, not rejected:** it front-loads the least certain bet (developers may want
to read this catalog and never want it failing their CI), and it is strictly a layer on top
of B's data artifact, so nothing is lost by waiting.

## Recommended Approach

**Approach B.** A schema is the only thing that keeps 400 AI-written entries uniform, the
repo is empty so migration cost is zero, and B produces exactly the `catalog.json` that C
would later need.

### Identity model (resolves premise 1 and 2)

Three separate fields, because conflating them is what breaks status tracking:

- **`id`** — opaque, immutable, sequential, never reused, never renumbered: `SDLC-0142`.
  Carries no category meaning, which is the point: re-categorizing a process creates no
  pressure to renumber it. This is the key `catalog.json` and every user's status file use.
- **`slug`** — immutable, unique across the whole catalog, flat namespace:
  `error-monitoring`. Drives the URL `/p/error-monitoring`.
- **`category` / `subcategory`** — mutable navigation metadata.

**URLs are flat and derived from `slug`, never from folder path.** This is the decision that
makes re-categorization free: move a file between folders and no URL and no status file
changes. Folders exist for editing convenience only.

Semantic IDs (`MON-003`) were considered and rejected: they read better, but they invite
renumbering on re-categorization, which is the exact failure premise 1 forbids.

### Entry template (deliverable 2)

Frontmatter carries only what gets queried, filtered, or indexed (the
[OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) rule); prose
lives in the body.

```yaml
---
id: SDLC-0142                  # immutable, opaque, never reused
slug: error-monitoring         # immutable, unique, drives /p/{slug}
title: Error Monitoring
category: monitoring           # mutable
subcategory: observability-signals
summary: One sentence, max 200 chars. Shown in listings and catalog.json.
lifecycle_phase: [operate]     # plan|design|build|verify|release|operate|govern
maturity: 2                    # 1 ad-hoc, 2 repeatable, 3 measured, 4 optimizing
effort: medium                 # low|medium|high
automatable: full              # none|partial|full
applies_to: [web, backend, mobile, data]
tags: [observability, reliability, incident-response]
related: [SDLC-0138, SDLC-0201]   # graph edges — premise 2
superseded_by: null
sources:                       # premise 4 — minimum 1, schema-enforced
  - title: "Google SRE Book, Ch. 6: Monitoring Distributed Systems"
    url: https://sre.google/sre-book/monitoring-distributed-systems/
    type: book                 # standard|book|vendor-doc|paper|practice-report
status: published              # draft|review|published|deprecated
generated_by: claude           # provenance — premise 4
reviewed_by: jelnur            # required before status can become published
last_reviewed: 2026-08-19
---
```

Required body headings, enforced by the linter so every entry has the same shape:

1. `## Purpose` — why this exists, what breaks without it
2. `## What Good Looks Like` — observable end state, not aspiration
3. `## Best Practices` — bulleted, each independently actionable
4. `## Automation` — how to automate it, with a concrete CI snippet where one exists
5. `## Signals & Metrics` — what to measure to know it is working
6. `## Anti-Patterns` — the common wrong version
7. `## Tooling` — tool categories plus named examples, vendor-neutral
8. `## Getting Started` — the first three steps for a team at maturity 1
9. `## References` — expanded from `sources`, plus further reading

Sections 6 and 8 are what separate this from an awesome-list. Keep them mandatory.

### Status tracking (deliverable 4, resolves premise 3)

`status.schema.json` defines a file that lives in the **user's** repo. No backend, ever.

```yaml
catalog_version: "2026.08.1"      # lets consumers detect drift
project: acme-payments
updated: 2026-08-19
processes:
  SDLC-0142:
    state: implemented            # not-started|in-progress|implemented|not-relevant|waived
    owner: platform-team
    evidence: https://github.com/acme/payments/blob/main/.github/workflows/alerts.yml
    note: "Sentry + PagerDuty wired. Weak signal detection still manual."
    reviewed: 2026-08-19
  SDLC-0201:
    state: not-relevant
    rationale: "No mobile surface."   # REQUIRED for not-relevant and waived
```

`rationale` being required on `not-relevant` and `waived` is what keeps the checklist honest
instead of a way to mark everything N/A.

The interactive tracker page (load a status file, tick boxes, download it back, DSOMM-style)
is the one deferrable piece of B. The schema is what deliverable 4 actually asks for
("suitable for future collaboration features"), and the schema costs an afternoon.

### AI generation (deliverable 6)

Two skills, deliberately split, because "what should exist" and "write it well" are different
jobs and merging them is what makes 400 entries unreviewable.

**`catalog-expand` (breadth).** Given a category or the whole tree, propose every process
that belongs, at maximum scope. Writes candidates to `catalog/_meta/taxonomy-backlog.yaml`
with `id: null`, `proposed_title`, `proposed_category`, `rationale`, `sources_hint`,
`confidence`, `duplicate_of`. It writes no entries. The user marks each
`approved | rejected | merged`; approval assigns the next sequential ID.

**`catalog-write` (depth).** Takes one approved backlog item, researches real sources, writes
the full entry against the schema and the nine headings, runs `scripts/validate.mjs` on it,
and opens a PR with `status: review` and `generated_by: claude`. One PR per entry so review
stays possible. The user flips `status: published` and sets `reviewed_by`.

**Hard rule in `catalog-write`, non-negotiable (premise 4):** every `sources[]` entry must be
a URL the skill actually fetched in that session. If no real source supports a practice, the
item returns to the backlog as `needs-evidence` rather than shipping. This is the guard that
keeps AI generation from manufacturing plausible-sounding practices.

### Contribution policy (deliverable 5)

Named `CONTRIBUTING.md`, not `collaboration.md`: GitHub surfaces `CONTRIBUTING.md`
automatically in the PR composer and the repo sidebar, and a non-standard filename loses that
for nothing.

It must state:

- **What a human PR is for:** corrections, real-world evidence, tool references, processes
  the generator missed, translations. Not bulk new entries.
- **Two paths by cost:** propose a process via the structured issue form (cheap, feeds the
  backlog) versus write or fix an entry via PR (uses the template).
- **AI-authorship disclosure:** this catalog is machine-generated and human-reviewed, every
  entry declares `generated_by`, here is why, and here is how to challenge an entry.
- **The schema contract:** CI rejects PRs that break it; run `npm run validate` locally.
- **ID rules:** never invent one, never change one, never reuse one.
- CODEOWNERS plus branch protection so AI-authored PRs still require human approval.

### Beyond the brief (deliverable 7)

Things worth doing that were not in the original list:

- **Ship `llms.txt` and `catalog.json`.** The second audience is agents. Cheap, and it makes
  the catalog useful in a way no awesome-list is.
- **Deprecate, never delete.** `status: deprecated` plus `superseded_by` keeps IDs valid
  forever, which premise 1 requires.
- **Split the license.** MIT for `scripts/`, CC BY 4.0 for catalog content, both stated
  plainly. Most catalog projects get this wrong at first and it is painful to change once
  contributors have signed on to the wrong terms.
- **Seed depth before breadth, then go public.** Do not publish at 20 entries. Take three
  categories to full depth (~40 entries) first. Depth in a few categories reads as serious;
  broad-and-shallow reads as abandoned.
- **State anti-goals in the README.** Not a maturity certification, not a compliance
  framework, not a tool directory. This is what stops contributors pulling the project in
  three directions.
- **CI-generated count badge** ("412 processes across 18 categories"). The single cheapest
  strong signal of the project's value.

## Open Questions

1. **Does the nine-section template survive contact with an unusual process?** Genuinely
   unknown until you hand-write one. If `## Automation` is empty for a governance process,
   the template needs an "N/A with reason" convention rather than an empty heading.
2. **Where does the category tree stop?** "Monitoring" and "Testing" are clear. Is "Hiring
   and onboarding engineers" an SDLC process? A stated inclusion rule in `categories.yaml`
   prevents the taxonomy sprawling in review.
3. **Starlight or Material for MkDocs?** Recommending Starlight: built-in search with no
   server, roughly 50KB JS per page, and you will want custom components for the tracker and
   the category matrix. Material for MkDocs is the equally safe pick if you would rather stay
   in Python. This is reversible and low stakes; the content layer does not care.
4. **How many entries before public?** ~40 across three categories is the recommendation, not
   a validated number.

## Success Criteria

- 400+ processes, every one schema-valid with at least one real cited source.
- Adding a process is one skill invocation plus one human review, under 10 minutes.
- CI rejects any PR that breaks the frontmatter contract or reuses an ID.
- `catalog.json` is consumable by a third party without reading the repo.
- Re-categorizing a process changes no URL and no user's status file. Test this deliberately.
- A stranger can tell within 30 seconds what the project is and is not.

## Distribution Plan

- **Site:** GitHub Actions builds Starlight, deploys to GitHub Pages on push to `main`. $0.
- **Data:** `publish.yml` on a version tag builds `catalog.json`, `catalog.yaml`, and
  `llms.txt` and attaches them to the GitHub Release. Date-based versioning (`2026.08.1`) so
  consumers can pin.
- **PR gate:** `validate.yml` runs schema validation, heading lint, ID uniqueness and
  immutability (diffed against `main`), link integrity, and source presence.
- **Later (approach C):** npm/PyPI package plus `sdlc-check` CLI and README badge, built on
  the release artifact. Deferred until the catalog has depth.
