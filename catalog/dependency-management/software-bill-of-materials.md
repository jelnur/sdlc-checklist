## Purpose

Answer "what is in the thing we shipped" in seconds. When the next widely-exploited library
vulnerability is announced, the useful artifact is an inventory you already have, not a
weekend of grepping.

## Examples

- A CycloneDX document produced by the build for every release artifact and attached to the
  release.
- Nightly scanning of stored SBOMs against a vulnerability feed, so newly published CVEs
  match against already-shipped versions.

## What Good Looks Like

Every released artifact has an SBOM generated by the build that produced it, stored and
retrievable by version, including transitive and container-base components.

## Best Practices

- Generate at build time from the actual build, not by re-scanning source later.
- Emit a standard format, SPDX or CycloneDX, so any tool can read it.
- Include transitive dependencies and container base-image contents.
- Store it with the artifact and keep it for as long as that version is supported.
- Sign or attest it, so the inventory itself can be trusted.

## Automation

Fully automatable: generation in the pipeline, storage alongside the artifact, and continuous
matching against vulnerability feeds.

## Signals & Metrics

Share of released artifacts with a stored SBOM, time to answer an exposure question, count of
components with no known upstream, and mean age of direct dependencies.

## Anti-Patterns

- Generating an SBOM once for an audit and never again.
- Direct dependencies only, which misses where most of the risk lives.
- An SBOM produced but never queried, so nothing is gained when it matters.
- A proprietary format only one vendor's tool can read.

## Tooling

Syft, Trivy, `cdxgen`, or native support in Maven, Gradle and `npm`; Dependency-Track or
Grype for continuous matching; Sigstore Cosign for attestation.

## Getting Started

Add an SBOM generation step to the pipeline for your most important service, attach the
output to the release, and point a vulnerability scanner at the stored documents.
